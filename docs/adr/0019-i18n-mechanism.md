# ADR 0019：多語系的機制（D9.1）

- 狀態：已採用（2026-09-30）。使用者決定：3a-1 之前先處理機制（phase3-plan §6 決定 6）。
- 範圍：**機制、檢查、驗證用的轉換**。英文翻譯留到 3a-9；既有字串**尚未全部搬**，由「只減不增」的檢查逐步搬（見 §3）。

## 1. 問題

介面文字與錯誤訊息寫死在約 750 行程式碼裡，分成兩類：

- `apps/web` 的標籤、提示、通知（約 450 行）；
- `packages/*` 丟出的訊息（`CommandError`、`FeatureError`、核心與草圖的錯誤，約 300 行）。這些在 **Worker** 裡產生（重算的錯誤與警告），經 `FeatureResult.message` 傳回畫面。

之後每個新功能都會再加字串；不先有機制，搬的成本只會增加。

## 2. 決策

| # | 決策 | 理由 |
|---|---|---|
| 1 | **新套件 `@3db/i18n`**：零依賴，最底層，所有套件都可以匯入（`check-deps` 的 `ALLOWED` 表加入）；主執行緒與 Worker 各有一份實例 | 訊息在兩個執行緒都會產生；套件層的訊息不能反向依賴 `apps/web` |
| 2 | **語意鍵加樣板**：`t('cmd.featureNotFound', { id })`；鍵是 `<區域>.<名稱>`，說的是用途不是內容，改字或翻譯不會改鍵。樣板用 `{name}` 佔位 | 鍵穩定，翻譯者不必動程式碼 |
| 3 | **編譯期檢查佔位**：`t` 的參數型別由樣板的 `{…}` 推出來，少給、多給、名稱寫錯都編譯不過；沒有佔位的訊息不接受參數（測試以 `@ts-expect-error` 釘住） | 譯文與程式碼最常見的錯是參數不合，讓它在編譯時就失敗 |
| 4 | **繁體中文是唯一的來源語言**（`zh-TW` 目錄，依擁有者分檔：`ui.ts`、`model.ts`…）；其他語言是**部分翻譯**，沒翻的退回中文，不出現空白或鍵名 | 使用者是中文使用者，術語採 SW 2010 繁中版；英文可以逐步補，不會因為缺一條就壞 |
| 5 | **訊息在產生的當下就用當時的語言解析成字串**，不帶著「鍵加參數」流過各層。語言切換後，Worker 已經算出的訊息還是舊語言，所以 `store.setLanguage` 會通知 Worker 再重算（重算會重新產生所有訊息） | 訊息是衍生資料（不存檔），重算本來就便宜；若改成傳遞「鍵加參數」，`FeatureResult.message` 等型別、每個使用處、測試都要改，成本遠大於收益。代價：舊語言的訊息在下一次重算前仍在畫面上（切換語言本身就觸發重算，實際上看不到） |
| 6 | **標籤表（`FEATURE_LABEL` 這類模組層級的表）用 `labelsOf`**：物件的每個屬性是 getter，讀取時才查目前的語言；`App` 以 `useSyncExternalStore` 訂閱語言，切換時整棵樹重繪 | 呼叫端不用改（`FEATURE_LABEL[f.type]` 照舊），也不會有「載入時凍結成一種語言」的錯 |
| 7 | **語言的選擇存在 `localStorage`（`locale`）**，沒有選擇就用預設 `zh-TW`；**不使用瀏覽器的語言**，直到英文有實際的翻譯 | 現在選 `en` 只會看到中文，用瀏覽器語言預設只會造成困惑。切換介面（設定畫面）留到 3a-9 有翻譯時做；`store.setLanguage` 已可用 |
| 8 | **`<html lang>` 跟著語言** | 螢幕閱讀器、字型與斷行的選擇 |

## 3. 「只減不增」的檢查（`npm run lint:i18n`，含在 `npm run check`）

`scripts/check-i18n.mjs` 數每個檔案裡「有中文字元的程式碼行」（註解與 `zh-TW` 目錄本身不算），與 `scripts/i18n-baseline.json` 比：**某個檔案可以變少，不可以變多；沒列在基準裡的檔案不可以有任何一行**。新程式碼因此只能用 `t()`。搬完一個檔案後執行 `node scripts/check-i18n.mjs --update` 把數字降下來（升高會被拒絕）。

起點是 **639 行、39 個檔案**（轉換前約 750 行；本 ADR 搬了 `strings.ts`、`expr.ts`、`commands.ts` 共 111 行）。

**不做的替代方案**：一次搬完全部。它會是 750 行的機械式大改動，沒有任何使用者看得到的好處（英文還不存在），卻要在沒有英文對照的情況下決定每一個鍵的名字；與新功能穿插搬，每個檔案在有上下文時搬、搬完立刻有型別與測試把關。**代價**：在搬完之前不能把介面換成英文；3a-9 之前要把這個基準降到 0 或決定留下哪些檔案。

## 4. 規則（給之後的程式碼）

1. 新的使用者可見文字一律 `t('區域.名稱', {…})`，文字寫進 `packages/i18n/src/zh-TW/<擁有者>.ts`。
2. 不要拼接句子：`${label}需要…` 這種寫法在英文會壞。需要組合時，讓整句是一條訊息，變動的部分當參數（參數本身可以是別條訊息的結果，例如 `cmd.needsEarlierSketch` 的 `feature`）。
3. 不要在別處判斷「目前是不是英文」；差異放進訊息樣板。
4. 單位、符號與數字格式（`mm`、`°`、`(-)`）不是文字，不放進目錄。
5. 譯文必須保留與來源相同的佔位名稱（加入英文目錄時，測試逐條檢查）。

## 5. 驗證

- `packages/i18n/test/i18n.test.ts`（10 項）：填入參數、編譯期參數檢查、退回中文、佔位可搬動、缺參數時不印出 `undefined`、語言變更通知、標籤表跟著語言、來源目錄的格式（鍵名、佔位、大括號）。
- `packages/model/test/model.test.ts`：被拒絕的指令以目前語言說明；沒翻的仍是中文。
- 瀏覽器：註冊三條英文後 `store.setLanguage('en')`：設計樹的原點與前、上基準面立即變英文，沒翻的右基準面仍是中文，`<html lang>` 變 `en`，設定被記住並觸發重算（三個特徵仍 ok）；切回後恢復。
- 檢查腳本的負向測試：在 `history.ts` 多加一行中文字串，`lint:i18n` 失敗並指出檔案與行數。
- **未驗證**：Worker 端的訊息實際變成英文。目前 Worker 產生的訊息（`regen`、`kernel`、`sketch`）都還沒搬，`setLocale` 只驗證了呼叫成功。這一項要在搬 `packages/regen` 時驗證（測試：以 `en` 重算一份壞文件，訊息是英文）。

## 6. 之後

- 搬：`packages/regen`、`kernel`、`sketch`、`io`（Worker 端訊息）優先，因為它們才需要跨執行緒；再來是 `apps/web` 的元件。
- 英文目錄（`packages/i18n/src/en/`）與設定畫面：3a-9。加入時一併加測試：每條譯文的佔位名稱與來源相同。
- 為 3a-1 準備：運算式的新錯誤訊息（循環引用、未知變數…）一開始就用 `t()`。
