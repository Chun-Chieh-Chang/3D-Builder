# ADR 0214：圓角結果的容差閘門

日期：2026-10-28。狀態：已實作；本機閘門與完整 `verify:ui` 見 §6；遠端 CI 待推送後的結果。檔案格式不變（不升 Schema）。

## 1. 問題

使用者回報（附畫面與檔案）：倒圓角之後，圓角的一端出現破孔。檔案是 `零件1.3dbx`：直徑 20、高 10 的圓柱，頂邊倒角 1 mm，再以兩段環形槽（r = 9 到 10，寬 1 mm，貫穿）切掉左右兩側的外壁，最後對四條豎直的槽角邊倒 0.5 mm 圓角。

## 2. 根因（先重現、量測，不猜）

在核心直接重建這個零件並逐步量測：

| 量測 | 結果 |
|---|---|
| 圓角前的形狀 | 邊與頂點的最大容差 1e-7、網格封閉（0 條開邊） |
| 圓角後（App 所得） | `BRepCheck` 判定**有效**、體積 2642.70（與畫面相同）；**一條邊的容差 18.09 mm**（零件對角線約 30 mm）；網格 24 條開邊，全部在同一個圓角面（`fillet1`）沿它與倒角錐面、頂面相接的邊界上 |
| 三種圓角形狀（Rational／QuasiAngular／Polynomial） | 全部同樣：容差 18.09、24 條開邊。換策略救不了 |
| 改網格參數（容差 0.0005～0.05、角度 0.1～0.5） | 開邊 22～48，不會變成 0 |
| `ShapeFix_Shape` | 容差仍 18.09 |

觸發條件（變化版本）：**倒角距離恰好等於環形壁厚（1 mm）**。倒角 0.5、1.1、1.5 mm 時圓角成功、網格 0 條開邊；0.8、0.9 mm 時圓角被明確拒絕（「半徑太大」）；1.0 mm 時，任何圓角半徑（0.2～0.8）都出問題。原因是倒角錐面頂端的圓邊（r = 9、z = 10）與槽底的圓弧（r = 9）重合，圓角終點正好落在這個重合的邊上，OCCT 的圓角運算回報完成，卻在那裡留下一條容差大到「兩側是同一個位置」的邊。

**為什麼沒被擋下**：`Kernel.fillet` 之前只用 `BRepCheck_Analyzer` 檢查結果。`BRepCheck` 對容差大小沒有意見，只要邊落在容差範圍內就算有效；18 mm 的容差範圍可以涵蓋整個零件。AGENTS.md §3.5 與 DEV_LOG 2026-10 已經為「圓角回報完成但實體損壞」加了 `BRepCheck`，這一例是它看不見的另一種損壞。

另一個觀察（**原因未查**）：同一個形狀在網格化之後再呼叫 `isValid`，結果由 true 變成 false。

## 3. 別的軟體怎麼做（讀原始碼）

| | 做法 |
|---|---|
| FreeCAD（Part 圓角） | 只檢查結果是否為空與例外，不檢查有效性或容差。 |
| FreeCAD（PartDesign 圓角） | 結果若 `BRepAlgo::IsValid` 不過，就用 `ShapeFix_ShapeTolerance::LimitTolerance` 把容差**靜默**壓到 `Precision::Confusion`（1e-7）。 |
| SolidCraft | 用 Rust 的 `truck` 而不是 OCCT，沒有「容差被放大」的問題，沒有可比的檢查（有的是圓角後的共面合併，以及「倒角太大」被拒絕的測試）。 |

我把 FreeCAD PartDesign 的做法直接套在這個零件上：容差壓到 1e-7 之後，形狀變成**無效**（`isValid` false），網格仍有 17 條開邊。邊離面真的有 18 mm 遠，把容差數字壓小不會讓它回到面上。所以不採用。

## 4. 決策

`Kernel.fillet` 在 `BRepCheck` 之後，再讀結果的最大容差（所有邊與頂點，OCCT 的 `BRep_Tool::Tolerance`）：**大於「這次圓角用到的最小半徑」的 0.25 倍就拒絕**，並說明（`feature.filletTolerance`：容差多大、半徑多小、常見原因、怎麼辦）。三種圓角形狀都會試，這個檢查在每一種裡面；全部不過，丟出最後一個錯誤。可變半徑的圓角用其最小的控制半徑。

**門檻的依據**（量測，不是任意）：完整測試套件裡的 502 次圓角（不含我自己的探針）：容差中位數 1e-7、第 95 百分位 1e-4；最大的 7 次是 0.024～0.025 mm（半徑 0.5，是半徑的 5 %；零件約 33 mm，是哪幾個測試沒有追查），**網格 0 條開邊**，不受影響。壞的那一個是 18.09（半徑的 36 倍）。0.25 在兩者之間，離最大的正常值有 5 倍餘裕。

## 5. 紅隊四問

1. **輸入破壞**：半徑不變；沒有 `Math.round` 或默默改值。倒角距離等於壁厚的組合現在是明確的錯誤。可變半徑以最小控制半徑為尺度。
2. **幾何相交**：這正是「相鄰特徵的邊重合」的例子；沒有在前置階段攔截（要預先判斷圓角終點是否落在另一個特徵的邊上，需要一套通用的幾何判定），而是在結果階段攔截，並說明常見原因。
3. **依賴鏈**：`kernel.ts`（`maxTolerance`、`FILLET_TOLERANCE_RATIO`、`Kernel.fillet`）→ 雙語字串；重建器已經把核心錯誤顯示為特徵錯誤，不用另外接。不改 schema、命令、DAG。
4. **零 Mock**：真實的使用者檔案（`tests/fixtures/fillet-chamfer-equals-wall.3dbx`）、真實的核心與重建器；真值是 OCCT 自己的 `BRep_Tool::Tolerance` 與一個獨立的網格開邊計數（自己焊接頂點，不使用核心的任何判定）。

| | **150 組隨機（倒角與半徑，一半落在重合的 1 上）** | 成功的圓角網格 0 條開邊、容差 ≤ 0.25 倍半徑；被拒絕的一定有訊息；成功與被拒絕各 > 15 次（避免單邊假綠） |

**反向對照**（已還原）：把門檻設成極大，11 項裡 7 項轉紅（原檔、五個半徑、150 組隨機）。

**全量結果**：`npm test` 3744 項通過、5 項失敗（與 ADR 0211 在乾淨 HEAD 重現的是同一 5 項）；靜態閘門（型別除外：只有他人未追蹤的 `zz-hlr-spike.test.ts` 的 TS6133）、i18n、repo 完整性通過；完整 `verify:ui` 239 個腳本 224 通過、15 失敗，**失敗名單與 ADR 0211 在乾淨 HEAD 重現的 15 個完全相同**。

**過程中要更正的一件事**：我曾說「測試套件裡已經有同樣幾何的圓角」。那是錯的：記錄裡容差 18.09 的兩筆來自我自己的探針測試（探針是 gitignored 的檔案，仍會被本機的測試跑到），不是既有測試。所以**目前只有一個已知會壞的零件族**（使用者的這個）；門檻的「壞的那一側」只有這一個量測，不是統計。

## 7. 已知限制
- **倒角（`Kernel.chamfer`）沒有任何有效性檢查**，連 `BRepCheck` 都沒有，也沒有容差檢查。同樣的重合在倒角上可能出同樣的問題；這次沒有量測，所以沒有改。
- 門檻 0.25 倍半徑是介於兩群量測之間的判斷，壞的一側只有一個零件族。容差沒有放大、卻仍破孔的損壞不會被這個檢查擋住。
- 圓角後再網格化發現的開邊（`isValid` 在網格化後變 false 的原因）沒有查；一個更直接的檢查是在重建後驗證網格封閉，但成本與誤報風險（有的零件本來就有開放的曲面）要另外評估。
- 使用者目前的零件會從「有破孔但顯示出來」變成「圓角失敗並說明」；要讓它成功，需要略微改變倒角距離、圓角半徑，或相鄰的壁厚。
