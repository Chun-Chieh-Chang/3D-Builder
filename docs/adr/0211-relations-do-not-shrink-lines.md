# ADR 0211：關係不能靠把直線壓成一個點來滿足

## 1. 背景
使用者回報：草圖直線建立成垂直，其中一端標註尺寸之後，垂直的性質變了、沒標註的那一端還在原地，整條線歪了；「類似這樣的問題不知還有多少」，要求水平展開檢視，不要只查垂直線。

**這份 ADR 記的是水平展開檢視找到並修掉的一整類問題；使用者原本那一個具體的畫面沒有被重現**（見 §6）。

## 2. 調查（先量測，不猜）
1. **求解器本身對單純案例是對的**：垂直線加標註，整條線一起平移並保持垂直；沒有垂直關係時才會歪（作為對照）。用介面流程重現（畫垂直線、從原點標註一端）也是對的：關係與尺寸都保留。
2. **矩陣掃描**（14 組關係 × 8 種尺寸）：求解器回報「已解出」（`under`），但關係不成立的有 6 組。逐一印出發現：**關係的另一條線 `M` 被壓成一個點**（`c = d`）。
3. **根因**：PlaneGCS 的平行、正交、共線等關係的殘差**沒有正規化**（正交是兩條線方向向量的內積，平行是外積）。長度為 0 的線，內積與外積都是 0，所以「把線壓成一個點」是這些關係的一個數學上合法的解，而且往往是離起點最近的解。求解器走最短的路，就把一條線壓扁，並回報成功。
4. **UI 層隨機掃描**（用真實的 `SketchController`：畫線與推斷關係、提供的關係、智慧尺寸、改值、拖曳；真實求解器）：150 個流程裡 **24 次線被壓成長度 0、4 次關係不成立、3 次過度定義**；0 次關係消失。最單純的一例：畫一條垂直線 `l1`，再從它的下端畫一條斜線 `l2`，對兩條線加「平行」，**原本畫好的垂直線 `l1` 變成一個點（25 → 0）**，介面卻回報「已加入」，因為 `addRelation` 只拒絕 `over`／`failed`。

## 3. 決策
1. **求解器加「退化守門」**（`PlaneGcsSolver.solve`）：原本長度 ≥ 0.01 mm 的直線，解出來若 < 0.0001 mm，這個解不被接受。
2. **先用「保持長度」再解一次**，讓關係以轉動或移動來滿足，而不是壓扁：
   - 每條有長度的線各加一個暫時的距離限制（保持原長，求解器內部的 `@keep:` 限制，不進文件）；
   - **只保護被壓扁的那條不夠**：實測求解器會改成壓另一條（`L` 縮到 0.0085），所以保護所有有長度的線；
   - 有的線的長度本來就由使用者的尺寸或關係決定，保護會衝突：求解器指出衝突的保護，**一次放掉一條**（優先放掉沒被壓扁的，被壓扁的最後放），重解；
   - 起點的奇異性：水平線要變垂直時，保持長度與「垂直」的梯度方向相同，求解器誤判為衝突。重解前把每條被保護的線繞第一個端點**各轉不同的小角度**（約 1°，長度不變），避開奇異組態；兩條原本平行的線若轉同一個角度仍然平行，所以每條不同。
3. **回傳保護後的解**；自由度與衝突診斷取自「不含保護」的系統（用保護後的位置為起點再解一次），但**不回傳那次的幾何**：兩條線重疊成一條時，沒有限制長度，再解一次會沿著自由方向亂滑（25 → 25.067）。
4. **還是壓扁就拒絕**：重解失敗或仍有線被壓成點（例如對同一條線既水平又垂直，唯一的解就是長度 0），整次求解回傳 `failed`，`collapsed` 列出是哪些線，訊息說明「這會把直線『…』壓成一個點」。回傳的是**儲存的原始位置**（和其他求解失敗一致），不是空的，也不是壓扁的解。
5. **介面**：`addRelation` 與 `placeDimension` 在 `failed` 且有 `collapsed` 時顯示這則訊息，而不是籠統的「過度定義」。
6. **只管直線**：掃描只在直線上看到壓扁。圓與圓弧沒有觀察到案例，不為沒有證據的路徑加沒測過的程式。
7. **不變的**：沒有被壓扁的求解完全走原來的路（沒有額外求解，結果不變）。

**實作與測試過程中的錯**：
- 第一版只保護被壓扁的那條線，求解器改壓另一條（0.0085，沒低於當時 1e-6 的門檻），所以改成保護全部、放掉衝突的。
- 第一版一次放掉所有被指出衝突的保護，結果什麼都沒保護；改成一次一條。
- 第一版對所有被保護的線轉同一個角度，兩條原本平行的線仍平行、仍是奇異組態；改成各轉不同的角度。
- 第一版回傳「不含保護」重解的幾何，在重疊的線上亂滑；改成回傳保護後的解。
- 守門失敗時第一版回傳空的幾何，改尺寸觸發時整張草圖會從畫面消失；改成回傳儲存的位置。
- 測試第一版：以為圓與直線可以 `equal`（規則禁止）；把「解不唯一」的情境寫成唯一解（共用端點可以往兩邊動；兩條重疊的線長度沒被限制）；沒注意到畫水平線時介面已推斷「水平」，再加「垂直」本來就矛盾。

**全量結果**：`npm test` 3712 項通過、5 項失敗；完整 `verify:ui` 236 個腳本 221 通過、15 失敗。這些失敗在不含本次變更的乾淨 HEAD（`46d71b3`）上以相同指令重現，失敗訊息相同，不是本次造成（清單見 `DEV_LOG.md`）。其中 `manual-c6` 與 `phase3-sketch-checks` 的訊息是找不到「改為從動」按鈕，與草圖診斷相關，已特別對照乾淨 HEAD；成因未查，不在本 ADR 範圍。

## 5. 已知限制
- 只守直線的長度。圓與圓弧沒有觀察到被壓成點的案例，沒有守門，也沒有測試。
- 解不唯一時，解的位置會隨求解器內部狀態而不同（共用狀態下 x 可能是 7.05 或 8.89）。這是既有的性質（`PlaneGcsSolver.fresh()` 就是為了重建的確定性），守門沒有改變它。
- 「一致卻被拒絕」的組合都只出現在**含有多餘關係**的組合裡（關係彼此蘊含，本來就是過度定義）；獨立的組合沒有被錯拒。這只用方向關係（垂直、水平、平行、正交）驗證過，共線、相等、中點、重合、相切等沒有同樣的獨立判定。
- 閾值：原本 ≥ 0.01 mm、結果 < 0.0001 mm 才算被壓扁。使用者把線標成 0.05 mm 是允許的。

## 6. 沒有重現的部分
使用者描述的是「垂直線，標註一端後歪了」。在垂直線單獨加標註、以及加上原點水平推斷的流程裡，**求解器與介面都是對的**，沒有重現。這份修法解決的是同一類現象（關係被默默破壞、介面說成功）的實際案例，其中也有垂直線被破壞（#84：垂直線被壓成點）。如果使用者的畫面是別的成因，需要那張草圖的檔案或確切步驟（用了哪些關係、標註了哪個點、哪一種尺寸）才能重現；這個類別的掃描已經能抓到「關係消失」「關係不成立」「線被壓扁」，目前除了本 ADR 處理的，沒有再找到。
