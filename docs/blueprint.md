> **文件狀態：v1.1**｜SW 全系統拆解 → 四輪取捨（含「模具不做、夾治具要做」的更正）→ 藍圖 已完成｜保留原規劃與範圍；交付狀態見[產品現況](project-state.md)

## 0. Context

- **要解決的事**：自建一套類 SolidWorks（下稱 SW）的參數式 3D CAD，範圍對標「SW 早期基礎建模能力」，並延伸到你的三個產業流程：**夾治具（加工夾具、組裝治具、檢具）→ 塑膠件 → 鈑金**。模具設計不做。
- **原始需求（R1–R6）**：基本草圖｜從草圖長出 3D｜SW 式參數化互動介面｜結合關係與父子關係｜輸出 STEP｜功能邏輯基於 SSOT 與 MECE。追加：**R7 與 SW 資料互通**（大量輸入既有 STEP 並繼續修改）、**R8 產業流程**（夾治具、塑膠件、鈑金）。
- **規劃時的原始起點（歷史）**：`<使用者資料夾>\Downloads\3D-Builder` 為空目錄、非 git repo；全新專案，無既有程式碼可重用。
- **參考資料**：SW 2010 繁中說明文件（34 章目錄已逐章讀取，術語與完整性已校正，見附錄 B.4）。
- **預期成果**：
  - 約 3–4 個月（Phase 1）：可用的「零件參數建模 + STEP 往返」版本。
  - 約 9–13 個月（Phase 4a）：可做加工/組裝夾具。
  - 約 15–23 個月：完成全部階段。
  - 以上為粗估，可信度低。

## 2. 架構藍圖

### 2.1 技術棧（依實作校正，原選型歷史見ADR0002、0003）

| 層 | 選擇 | 理由 |
|---|---|---|
| 幾何核心 | **libcascade預建OCCT WASM + TypeScript門面**（版本由lockfile與ADR0003記錄） | 採用完整綁定以覆蓋建模與輸出；早期選型／缺口驗證保留於ADR0002、0003 |
| 核心執行 | Web Worker + Comlink；網格以 Transferable ArrayBuffer 回傳 | UI 不被重新計算阻塞（B3.5） |
| 草圖求解 | **PlaneGCS**（FreeCAD 草圖求解器，LGPL）編成 WASM，包在 `Solver2D` 介面後 | 已在 FreeCAD 實戰驗證；提供 DogLeg/LM、冗餘/衝突診斷與相依參數分析（逐圖元完全定義著色）。備案：libslvs（GPL，內部使用可）或自研 |
| 結合求解 | **自研 TS 求解器**（每零組件 6 DOF、Levenberg-Marquardt、依連通分量分解、SVD 算剩餘 DOF；限制結合用不等式處理） | A2 + 限制/寬度/相互對稱結合，自研最可控 |
| 繪圖 | Three.js（WebGL2）+ three-mesh-bvh（拾取）+ 粗線段（邊線） | 成熟、MIT 授權 |
| UI | React + TypeScript strict + Vite（實際版本見lockfile） | 介面開發最快、AI 輔助最成熟 |
| 狀態 | 文件 = 不可變資料（Immer patches 做復原/重做）；衍生快取另存 | SSOT：文件與衍生資料實體分離 |
| 檔案 | `.3dbx` = ZIP（`document.json` 穩定排序 + `blobs/` 輸入的 STEP + 可選 `cache/`） | JSON 可 diff（B9.6）；輸入的 STEP 是設計意圖的一部分，必須隨檔保存 |
| 本機存取 | File System Access API（Edge/Chrome）；Windows Tauri殼沿用同一前端檔案API | 組合件與衍生零件需要讀取資料夾內的其他檔案 |
| 測試 | Vitest（單元／金樣）、Chrome／Edge CDP驗收器（UI） | |
| 單一 repo | npm workspaces | package.json與package-lock.json為準 |

### 2.2 模組地圖與相依規則（程式碼層的 MECE）

  apps/desktop/          # Tauri 殼（Phase 3b）
  packages/model/        # SSOT：schema、文件指令、遷移、驗證（純 TS，零相依）
  packages/naming/       # 持久命名、參考解析、幾何指紋
  packages/sketch/       # 草圖模型、輪廓偵測介面、Solver2D 介面 + PlaneGCS 轉接
  packages/assembly/     # 組合件模型、Solver3D（自研）
  packages/regen/        # 重新計算引擎、父子 DAG、特徵快取、錯誤模型
  packages/kernel/       # Worker 協定 + OCCT 門面的 TS 型別
  packages/io/           # STEP/STL/DXF/PDF（DXF/PDF 以 TS 自寫/函式庫）
  packages/library/      # 標準件圖庫（本機 STEP 資料夾索引 + 參數化件產生器）（Phase 4a）
  packages/render/       # Three.js 場景、拾取、強調顯示、預覽
  packages/ui/           # 設計樹、PropertyManager、CommandManager、草圖編輯器

- **相依只能向下**：
  - `ui → render → kernel`
  - `ui → model`
  - `regen → model, naming, sketch, assembly, kernel`
  - `library → model, io`
  - `model` 零相依
  - 以上規則以 dependency-cruiser 在 CI 強制執行。
- **一個能力只屬一個套件**：每個套件在 README 列出自己負責的目錄 ID，例如 `naming` = B4，`regen` = B2、B3。

### 2.3 SSOT 資料模型（型別草案，`packages/model/src/schema.ts`）

```ts
type Id = string;      // 永久 ID（ULID），不隨順序或重新計算改變（B1.3）
type Expr = string;    // "20"、"D1*2"、"wall_t"、"25.4mm"（B5）

interface PartDoc {
  schemaVersion: number;               // B9.2 逐版遷移
  displayUnits: { length: 'mm' | 'in'; angle: 'deg' };   // 只影響顯示；內部固定 mm/rad
  variables: { id: Id; name: string; expr: Expr }[];      // 全域變數 + 數學關係式
  features: Feature[];                 // 有序歷史 = 樹狀結構（B2.1）
  rollbackIndex: number | null;        // 回溯控制棒（B2.4）
  properties: Record<string, string>;  // 檔案屬性（B8.3；標準件含廠商與料號）
  material?: MaterialRef;              // C14.1
  appearances: AppearanceOverride[];   // C14.2：零件 < 本體 < 特徵 < 面
  blobs: { id: Id; sha256: string; kind: 'step' }[];      // 輸入的原始資料
}

type Feature = FeatureBase & (
  | { type: 'sketch'; plane: Ref; entities: SketchEntity[]; constraints: SketchConstraint[] }
  | { type: 'extrude'; profile: ProfileRef; op: 'boss' | 'cut'; dir1: EndCondition; dir2?: EndCondition; draft?: Draft; thin?: Thin }
  | { type: 'revolve'; profile: ProfileRef; axis: Ref; op: 'boss' | 'cut'; angle1: Expr; angle2?: Expr }
  | { type: 'fillet'; targets: Ref[]; radius: Expr }
  | { type: 'chamfer'; edges: Ref[]; mode: 'dist-dist' | 'angle-dist'; a: Expr; b: Expr }
  | { type: 'refPlane'; mode: 'offset' | 'angle' | 'threePoint'; refs: Ref[]; value?: Expr }
  | { type: 'importedBody'; blob: Id; heal: boolean }
  | { type: 'derivedBody'; source: FileRef; body: Ref }   // Phase 4a：衍生零件連結主模型的本體（單向）
  // Phase 3a 起：sweep、loft、rib、holeWizard、shell、draft、linearPattern、circularPattern、mirror、combine、moveFace、deleteFace…
  // Phase 4b 起：offsetSurface、fillSurface、trimSurface、knit、thicken、cutWithSurface、splitLine
);
interface FeatureBase { id: Id; name: string; suppressed: boolean }

// 參考 = 持久名 + 幾何指紋；不存索引（B4）
interface Ref { kind: 'face' | 'edge' | 'vertex' | 'datum' | 'body'; name: string; fingerprint: Fingerprint }

interface AssemblyDoc {
  schemaVersion: number;
  components: { id: Id; source: FileRef; fixed: boolean; placement: Pose; suppressed: boolean; hidden: boolean }[];
  mates: { id: Id; type: MateType; a: CompRef; b: CompRef; value?: Expr; min?: Expr; max?: Expr; flip: boolean; suppressed: boolean }[];
  patterns: ComponentPattern[];
  explodedViews: ExplodedView[];
}
```

- **衍生資料永不進文件**：B-Rep、網格、元素對應表、草圖解、DOF 狀態、物質特性、錯誤清單。
- `placement` 記錄的是：使用者對「還沒被結合固定的自由度」怎麼擺，同時當作求解的初始值。求解後得到的位姿屬於衍生資料。
- 父子關係由所有 `Ref`、`ProfileRef`、`Expr`、`FileRef` 的引用即時推導，不另外存一份。
- 從圖庫插入標準件時，會產生（或重用）一個本機零件檔，內容是 `importedBody` 或參數化特徵，再加上廠商與料號屬性；組合件的零組件引用這個零件檔。

### 2.4 持久命名策略（TNP，第一天就做）

1. **機制在 C++、政策在 TS**：門面每次運算回傳「輸入子形狀 → 輸出子形狀」的演化表（取自 OCCT `BRepBuilderAPI_MakeShape::Generated/Modified/IsDeleted`、`BRepTools_History`）；`packages/naming` 依此產生名稱，方便單元測試。
2. **命名文法**：
   - 面以「生成來源」命名。例如 `F3:side:S2.e7` 是 F3 由草圖 S2 的圖元 e7 掃出的側面；`F3:cap:end` 是端面；`F5:fillet:<邊名>` 是圓角面。
   - 邊與頂點以「相鄰面名稱的集合」命名，例如 `{F3:side:S2.e7, F3:cap:end}`。
   - 布林運算後，面沿用 Modified 對應回來的名稱。
3. **分裂消歧**：一個面被切成多塊時，依它們相對分割特徵的幾何順序加上 `#1`、`#2`，並記錄消歧依據；有歧義就回報，不靜默猜測。
4. **解析順序**：
   1. 先找名稱完全相符的。
   2. 有多個候選時，用幾何指紋（類型、面積/長度、質心、法向）消歧。
   3. 找不到時標示「遺失參考」，列出指紋最接近的候選讓使用者重選（B4.3、D7.1）。
5. **輸入本體**：STEP 輸入的面依「blob 雜湊 + 拓撲索引 + 指紋」命名；只要來源檔不變，名稱就穩定。
6. **衍生本體**：名稱 = 衍生連結 ID + 主模型中的原名，例如 `L1>F12:side:S4.e3`。只要主模型的名稱穩定，組合件中對衍生零件的結合就穩定。

### 2.5 求解器策略

- **Solver2D**（`packages/sketch`）：
  - 輸入圖元與限制條件，輸出解、每個圖元剩餘的 DOF、冗餘/衝突清單。
  - 拖曳時以前一個解為初值，達到最小擾動（A2.6）。
  - 效能目標：100 個圖元的草圖在 16 ms 內解完。
- **輪廓偵測**：在門面以 OCCT `BOPAlgo_Tools::EdgesToWires/WiresToFaces` 產生區域（含巢狀內孔），回傳區域 ID 供 `ProfileRef` 引用。
- **Solver3D**（`packages/assembly`）：
  - 未知數：非固定零組件的平移 + 增量旋轉。
  - 結合：作用在轉換後特徵（點、軸、平面）上的殘差。
  - 限制結合：用不等式處理，超出範圍時以懲罰項/主動集方式處理。
  - 依連通分量分解問題，以 SVD 的秩求剩餘 DOF。
  - 過多定義時回報是哪些結合互相衝突（C15.12）。

### 2.6 重新計算引擎（`packages/regen`）

- **線性歷史**（同 SW）：`evaluate(feature, 上一個狀態, 已解析的參考) → { bodies, elementMap, errors }`。
- **快取與失效**：
  - 修改第 k 個特徵時，k 之後全部失效（本體狀態會向後傳遞）；k 之前重用快取。
  - 快取鍵 = hash（特徵定義 + 上游狀態雜湊）。
- **失敗隔離**：特徵失敗時跳過它並沿用前一個狀態，後續特徵照常計算，錯誤掛在樹節點上（B3.3）。
- **跨檔相依**（衍生本體、組合件）：來源檔變更時，依 `FileRef` 相依圖由下往上重算：主模型 → 衍生零件 → 組合件。
- **相依圖（DAG）的用途**：
  - 調整順序時的合法性檢查
  - 刪除時的連帶提示
  - 父子關係對話框
  - 動態參考視覺化
- **中止自動重新計算**（B3.7）：批次修改後再一次重算。

### 2.7 UI 佈局（沿用 SW 慣例，不使用其圖示與商標）

- **上方**：CommandManager 情境分頁（特徵｜草圖｜評估｜組合件；Phase 4 起加「夾治具」分頁：產生組合件、圖庫、餘隙確認）。
- **左側**：FeatureManager 樹狀結構 / PropertyManager 分頁、回溯控制棒；Phase 4a 起加圖庫面板。
- **中央**：圖面 + 立即檢視工具列 + 三度空間參考 + 確認角落（確定/取消）。
- **下方**：狀態列（草圖幾何狀態、單位、重新計算狀態）。
- **滑鼠**：中鍵旋轉、Ctrl+中鍵平移、滾輪縮放（方向可設定）。
- **UI 動作**：全部由 `D3.1 UI 動作註冊表` 單一定義，並一律轉成 `B7.1 文件指令`。

### 2.8 STEP 管線（`packages/io` + 門面）

- **零件輸出**：最終本體 → XCAF 文件（名稱取自檔案屬性、顏色取自外觀覆寫）→ `STEPCAFControl_Writer`（預設 AP214，可選 AP242）。
- **組合件輸出**：每個零件一個原型標籤，每個實例是帶位姿的元件；次組合件巢狀 → STEP 產品結構。
- **輸入**：
  1. `STEPCAFControl_Reader` 讀入名稱、顏色、結構。
  2. `ShapeFix_Shape` 修復。
  3. `BRepCheck_Analyzer` 檢查。
  4. 零件成為 `importedBody` 特徵；組合件則展開成組合件 + 零件檔（Phase 3b）。

### 2.9 夾治具工作流（多本體主模型，Phase 4）

1. 新增主模型零件 → 輸入工件 STEP（`importedBody`，標記為「參考本體」，不進零件表）。
2. 以工件的面/邊為參考，建立基板、定位塊、壓板等本體（草圖、參考圖元、伸長、組合減除）；孔用異型孔精靈，包括 Phase 4a 新增的定位銷孔類型。
3. 檢具（4b）：選工件型面 → 分割線選出區域 → 偏移曲面（間隙）→ 填補/修剪/縫織 → 厚面，或以曲面除料，做出型面塊。
4. 「從本體產生組合件」：每個本體各產生一個衍生零件檔（`derivedBody`）+ 一個組合件（零組件位於原位並固定）。
5. 在組合件中從圖庫插入定位銷、螺絲、夾鉗，以標準結合定位；夾鉗動作用限制結合。
6. 驗證：干涉檢查、餘隙確認（工件取放空間）、拖曳時的碰撞偵測。
7. 輸出：STEP 組合件；Phase 5 起出零件加工圖與組合圖。
8. 設計變更只改主模型 → 衍生零件與組合件自動更新（SSOT）。

### 2.10 程式碼層的 SSOT/MECE 守則（寫進 `docs/adr/0001`）

1. 任何值只存一處；需要的地方以 ID 引用。

## 4. 驗證策略

> 下方`pnpm`／Playwright是規劃時的命令草案，實際可執行指令與測試器以[開發操作](development.md)及[盤點](repository-inventory.md)為準；不存在的命令不可直接照跑。

- **自動化**（每次提交執行）：
  - `pnpm test`：model、指令、遷移、naming、求解器轉接的單元測試。
  - `pnpm test:golden`：在 Node 中以 WASM 重建金樣文件，比對體積、面積、邊界方塊、面/邊數量，並跑 `BRepCheck` 有效性檢查。
  - `pnpm test:tnp`：做參數掃描（改尺寸、增刪草圖圖元、調整順序、修改主模型後重算衍生零件），確認每個參考依幾何指紋仍解析到正確的面/邊。
  - `pnpm test:step`：輸出 → 再輸入 → 比對體積、面積、邊界方塊與組合件結構。
  - `pnpm e2e`（Playwright）：畫草圖 → 標尺寸 → 伸長 → 圓角 → 改尺寸 → 輸出 STEP；Phase 4a 起加入「主模型 → 產生組合件 → 插入標準件」。
  - 遷移測試：每個舊版 schema 範例檔都能開啟。
- **人工對照**（每個階段閘門）：
  - 你在 SW 開啟輸出的 STEP，核對物質特性（體積、質心）。
  - 你用 SW 做同一個零件或夾具，比較建模步驟與結果。
- **效能預算**（Phase 0 實測後定案）：
  - 50 個特徵的零件，重算 < 2 s
  - 100 個圖元的草圖，拖曳求解 < 16 ms
  - 首次載入 < 10 s

## 附錄 A：第一性原理與 SSOT/MECE

**參數式 CAD 的本質**：`幾何結果 = Rebuild(設計意圖)`。設計意圖是輸入（SSOT），幾何是輸出（衍生資料）。

| # | 硬問題 | 客觀事實 | 架構約束 |
|---|---|---|---|
| H1 | 幾何核心 | STEP 實體要求精確 B-Rep；網格式布林只能輸出多面體 STEP，下游幾乎無法使用 | 採用 B-Rep 核心，不自研 |
| H2 | 約束求解 | 草圖（2D）與結合（3D）是兩套非線性系統；草圖幾何狀態需要 DOF 分析 | 求解器同時輸出解、剩餘 DOF、冗餘/衝突 |
| H3 | 拓撲命名（TNP） | 改參數後面/邊的數量與順序會變 → 參考斷裂（SW 稱遺失參考、模糊情形）。FreeCAD 直到 1.0（2024-11）才在主線緩解 | 第一天設計持久命名；禁止以索引引用 |
| H4 | 重新計算的確定性與效能 | SSOT 的前提是同輸入 → 同輸出 | 純函數 + 增量重算 + 快取 + 背景執行 |

**SSOT 落地**：
1. 唯一真相 = 設計意圖文件；夾治具的唯一真相 = 主模型。
2. B-Rep、網格、STEP、錯誤清單、衍生零件的幾何，都是衍生資料。
3. 父子關係由參考推導，不另存。
4. 一值一處、以 ID 引用、內部單位固定。
5. UI 不持有業務狀態，所有修改只經過文件指令層。

**MECE 落地**：
1. 模組互斥且窮盡：附錄 C 每一項只有一個擁有者；資料（B 層）與介面（D 層）分開列。
2. 特徵依「對幾何的作用」分類：增料、減料、修飾、複製、參考、本體運算。
3. 結合分為標準、進階、機械三類。
4. 消除 SW 自身的重疊：共用值併入全域變數、簡易直孔併入異型孔精靈。

## 附錄 D：AI 智囊團審查

### D.1 初審（對象：「自建類 SW 參數式 CAD」）

- **反駁者**：失敗點在核心穩健性、TNP、求解器，不在 UI。FreeCAD 到 1.0 才在主線處理 TNP；SolveSpace 刻意不做 3D 圓角；Onshape 選擇授權 Parasolid 與 D-Cubed。純網格方案輸出的 STEP 無法使用。
- **本質追問者**：為何不用 FreeCAD、Onshape 或 SW？「像 SW」是目標還是手段？SSOT/MECE 對使用者的可感知價值，要轉成可驗證的指標。
- **機會發現者**：
  - 以 FreeCAD 為底：最快，但受其架構約束。
  - 文字化 SSOT：Git 與 AI 都能讀寫，幾乎零成本就能內建。
  - 垂直產業利基。
  - Web 優先。
- **外行人**：打不開 SW 原檔（只能透過 STEP）；改尺寸會不會壞；當機會不會遺失作品；多久可以用。
- **無情執行者**：第一步是行走骨架（草圖 → 伸長 → 圓角 → 改尺寸 → 圓角仍在 → STEP 在 SW 驗證）。這條打不通就不做 UI。
- **主席結論**：【需要改】— 不自研核心、第一天設計持久命名、分階段；可信度 ≈ 70%。

### D.2 取捨後複審（對象：本藍圖 v1.1，含「模具不做、夾治具要做」的更正）

- **反駁者**：
  - 檢具的偏移曲面，是這份藍圖裡 OCCT 最可能失敗的操作。→ 已拆成獨立的 Phase 4b，開始前先做技術驗證。
  - 衍生零件引入跨檔相依。→ 以 B9.4 參考檔管理處理。
- **本質追問者**：「與 SW 互通」和「夾治具」其實是同一條工作流，都是輸入工件 STEP 再圍繞它設計。所以 STEP 輸入的品質（修復、命名穩定）比多做幾種特徵更重要。→ Phase 1 與 3a 的驗收都用你的真實檔案。
- **機會發現者**：
  - 多本體主模型讓夾治具的設計意圖集中在一個文件，這正是 SSOT。
  - 文字化格式日後可以用腳本批次產生系列化的夾具（例如同一族工件的定位板）。
- **外行人**：「3–4 個月就能用」指的是零件建模加 STEP 往返，還不是完整取代 SW；能做夾具要到第 9–13 個月左右。
- **無情執行者**：核准後第一件事，是 Phase 0 第 1 週：建好 OCCT WASM，在瀏覽器中顯示一個伸長方塊。
- **主席結論**：
  1. **判定**：【值得做（依階段閘門執行）】。
  2. **最大風險**：TNP 與 OCCT 穩健性（含檢具的偏移曲面），其次是範圍蔓延。
  3. **最缺的證據**：Phase 0 的 OCCT/WASM 實測數據，以及你的真實樣本檔案（零件、夾具案例、廠商標準件 STEP）。
  4. **今天最小的一步**：核准本藍圖 → `git init` → 開始 Phase 0。
  5. **可信度**：

     | 項目 | 可信度 |
     |---|---|
     | Phase 0–1 技術可行 | ≈ 85% |
     | 3–4 個月內完成 Phase 1 | ≈ 60% |
     | 13 個月內完成 Phase 4a | ≈ 45% |
     | 23 個月內完成全部階段 | ≈ 30% |
     | 本藍圖整體 | ≈ 70% |
